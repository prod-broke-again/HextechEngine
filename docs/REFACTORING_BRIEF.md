# Hextech Engine — Бриф на рефакторинг ядра

**Для кого:** AI-агент или разработчик, который будет составлять и исполнять план рефакторинга.
**Обязательное чтение перед началом:** `docs/ARCHITECTURE.md`. Этот документ без него бессмысленен.

---

## 1. Зачем вообще рефакторинг

Код пишется быстро и почти без ошибок, поэтому объём растёт быстрее, чем осмысляется структура. Через несколько таких сессий стоимость любого изменения вырастет нелинейно, и «переписать» станет дешевле, чем «поправить». Момент, когда рефакторинг ещё дёшев, — сейчас: ~200 КБ кода, два приложения, ни одного внешнего потребителя API.

Цель — **не красота**. Цель конкретна: после рефакторинга добавление новой игровой механики должно затрагивать **один новый файл модуля**, а не править семь существующих.

## 2. Диагноз текущего состояния

Каждый пункт — проверяемый факт, а не мнение.

### 2.1. Базовый класс `Application` — мёртвый код

`engine/core/include/engine/core/Application.hpp` объявляет класс с `Input`, `entt::dispatcher`, `Config`, `Time` и чисто виртуальным `run()`. `Application.cpp` содержит только дефолтные конструктор и деструктор.

**Ни `SandboxApp`, ни `EraApp` от него не наследуются.** Оба независимо объявляют те же самые поля и тот же цикл. Абстракция существует, но не используется — это худший вид мёртвого кода: он создаёт ложное впечатление, что каркас есть.

### 2.2. Событийной системы фактически нет

- `Events.hpp`: функция `registerCoreEvents(dispatcher)` содержит `(void)dispatcher;` — пустышка.
- Через `entt::dispatcher` во всём проекте ходит **ровно одно событие** — `WindowResizeEvent` (`EraApp.cpp:131`).
- Вся остальная связность — `std::function`-колбэки: `CitySimulation` имеет **шесть** сеттеров (`setOnBuildingPlaced`, `setOnBuildingRemoved`, `setOnCarrierSpawned`, `setOnCarrierRemoved`, `setOnEvolved`, `setOnBuildingStatusChanged`), каждый привязывается ровно к одному методу `EraApp`.

Утверждение из `SESSION_PROGRESS.md` — *«Симуляция полностью отделена от рендерера и ECS, все изменения транслируются через типизированные события»* — **не соответствует коду**. Шесть колбэков 1:1 к методам одного конкретного класса — это не отвязка, это жёсткая связь, спрятанная за `std::function`. `CitySimulation` не может существовать без `EraApp`, а `EraApp` обязан реализовать все шесть методов.

Отличить одно от другого просто: при настоящей шине событий можно добавить второго слушателя, не трогая источник. Здесь — нельзя.

### 2.3. Два источника правды — корневая проблема

```
CitySimulation:                       EraApp:
  std::array<CellData,32×32> m_grid     unordered_map<uint32_t, entt::entity> m_buildingEntities
  vector<BuildingInstance>              unordered_map<uint32_t, entt::entity> m_carrierEntities
  vector<CarrierAgent>                  unordered_map<uint32_t, entt::entity> m_alertEntities
```

Игровое состояние живёт в векторах симуляции. Визуальное представление — в ECS. Между ними — три руками поддерживаемые карты соответствия.

Последствия, которые уже видны и будут усугубляться:
- каждая новая сущность (юнит, эффект, дорога, декорация) добавит **четвёртую** карту;
- любое рассогласование карт = висящая или невидимая сущность, баг воспроизводится редко и ловится долго;
- сейв/лоад придётся писать **дважды** — для векторов и для registry;
- `unordered_map` по `uint32_t` **напрямую ломает выбранный детерминизм** (порядок итерации не гарантирован).

Это главная цель рефакторинга. Всё остальное — следствия.

### 2.4. Классы приложений — god objects

| Файл | Размер |
|---|---|
| `apps/sandbox/src/SandboxApp.cpp` | 61 КБ |
| `apps/era_sandbox/src/EraApp.cpp` | 44 КБ |
| `apps/era_sandbox/src/Simulation/CitySimulation.cpp` | 25 КБ |
| `apps/era_sandbox/src/Graphics/ProceduralCityMeshes.cpp` | 19 КБ |

Внутри `EraApp.cpp`:
- `renderUi()` — строки 608–943, **335 строк** одной функции;
- `updateFrame()` — строки 440–608, **168 строк**;
- `initEngine()` / `shutdownEngine()` — ручная инициализация десяти подсистем в правильном порядке и ручное разрушение в обратном, **продублированные** в `SandboxApp`.

`EraApp` одновременно: конфигуратор, инициализатор подсистем, обработчик ввода, рейкастер, менеджер сущностей, аниматор индикаторов, UI-слой и рендер-луп. Добавление подсистемы означает правку обоих приложений.

### 2.5. `SceneSerializer` не расширяем

`engine/ecs/src/SceneSerializer.cpp` — 15 КБ ручных if-цепочек по типам компонентов. Плюс `SceneResourceContext` — структура из **семи** `std::function`, которые приложение обязано заполнить, чтобы сериализатор смог создать коллайдеры, загрузить меши и т.д.

Добавление компонента = правка сериализатора. Добавление приложения = заполнение семи колбэков заново. Это ровно тот модуль, который должен строиться на рефлексии, а не писаться руками.

### 2.6. Фиксированный шаг есть, но не используется

`Time::consumeFixedSteps()` реализован (`Time.cpp:49`). Используется он ровно в одном месте — `SandboxApp.cpp:768`, и только для физики.

`EraApp::run()` игнорирует его полностью: `m_time.tick()` → `updateFrame(m_time.delta())` → `sleep` до 200 FPS. То есть вся экономическая симуляция города зависит от FPS. При выбранном полном детерминизме это неприемлемо и должно быть исправлено.

Отдельно: ограничение 200 FPS через `std::this_thread::sleep_for` — грубый инструмент (точность сна на Windows ~1–15 мс). После перехода на фиксированный тик проблема исчезает сама: симуляция идёт 30 Гц, рендер — свободно.

### 2.7. Хендлы ресурсов небезопасны

`MeshComponent { uint32_t mesh = UINT32_MAX; uint32_t baseColorTexture = kInvalidGpuTexture; }`.

Оба поля — `uint32_t`, компилятор не различит их при перепутанном аргументе. «Невалидность» кодируется `UINT32_MAX`, при этом валидный индекс 0 существует.

Это **уже дало реальный баг** (шаг 5 в `SESSION_PROGRESS.md`): проверка `if (meshId == 0) return;` блокировала создание лесопилки, потому что её меш загрузился первым и получил индекс 0. Симптом починили, причину — нет. Она воспроизведётся.

### 2.8. Ядро знает про игру

`engine/core/include/engine/core/InputMap.hpp`:

```cpp
enum class Action {
    MoveForward, MoveBack, MoveLeft, MoveRight, Sprint, Look,
    SpawnBox, SpawnTeapot, ShootSphere, KickObject, Jump,
    ToggleCameraMode, ToggleCursor, InspectObject,
};
```

Ядро движка содержит перечисление с чайниками и пинанием объектов. Прямое нарушение направления зависимостей: движок не должен знать ничего о конкретной игре. Для второй игры этот enum придётся либо засорять дальше, либо игнорировать.

### 2.9. Слои `core` смешаны

`engine_core` линкует `glm`, `EnTT`, `nlohmann_json` и содержит одновременно платформенные вещи (Log, Path, Time, Input, Config) и то, что должно быть foundation. `entt::dispatcher` торчит из `Application`, то есть платформенный слой знает про ECS-библиотеку.

### 2.10. Тестов нет вообще

`ENGINE_BUILD_TESTS` = `OFF`, каталога `tests/` не существует. Любой рефакторинг сейчас выполняется вслепую: единственный критерий корректности — «собралось и на глаз выглядит так же».

Для рефакторинга такого масштаба это неприемлемо. Тесты — не пожелание, а **предусловие этапа 1**.

## 3. Разбор предложенного ранее плана

Предыдущий план («Архитектурный рефакторинг Hextech Engine (Laravel-style API)») содержит верные интуиции и несколько ошибок, которые обойдутся дорого. Разбор нужен, чтобы эти ошибки не воспроизвелись.

### Что верно

- **`entt::dispatcher` как шина.** Правильный выбор: EnTT уже в зависимостях, отдельная библиотека не нужна.
- **UI не содержит бизнес-логики.** Верно и важно.
- **Изоляция намерений в отдельные единицы (Actions).** Верная интуиция, неверная реализация — см. ниже.
- **Отказ от буквального YAGNI применительно к инфраструктуре.** Направление верное, формулировка неточная (см. `ARCHITECTURE.md`, раздел 3).

### Что неверно

**1. Порядок работ перевёрнут.**
План начинает с Save/Load и Economy. Save/Load — **самый зависимый** модуль в движке: он требует готового реестра типов, стабильных идентификаторов ресурсов, версионирования схемы и решённого вопроса, где вообще живёт состояние. Сейчас состояние живёт в двух местах (п. 2.3) — сериализатор, написанный сегодня, придётся выбросить на этапе переноса состояния в ECS. Save/Load идёт **после** реестра типов и после унификации состояния, а не первым.

**2. Обещана несуществующая возможность.**
> «Должен уметь брать `entt::registry`, автоматически собирать все компоненты сущностей и дампить их»

`entt::snapshot` **не умеет** автоматически обходить компоненты. Он требует явного перечисления каждого типа в точке вызова: `snapshot.get<A>(out).get<B>(out)...`. В C++ нет рефлексии; «автоматически» не существует без слоя регистрации типов, который план не предусматривает. Реализация по этому плану упрётся в стену на первом же шаге — либо выродится в ту же ручную if-цепочку, что и сейчас.

**3. Стёрта граница между командой и системой.**
План предлагает «всё изолировать в классы с `execute()`». В Laravel Action — это один HTTP-запрос, его цена нерелевантна. В игре есть горячий цикл: тик производства обрабатывает сотни зданий каждый тик. Оформлять это как объект-команду — ошибка и по производительности, и по смыслу.

Правильное разделение (см. `ARCHITECTURE.md`, раздел 6):
- **Command** — дискретное намерение извне (0–100 за тик), валидируемое, отказуемое, сериализуемое.
- **System** — обработка массивов (каждый тик), без отказов, без создания сущностей напрямую.

**4. Не решён главный вопрос событийной архитектуры — синхронность.**
План говорит «системы не вызывают друг друга напрямую, используем dispatcher» и на этом останавливается. Но `dispatcher::trigger()` — **синхронный вызов**. Обработчик, срабатывающий посреди `registry.view()`, инвалидирует итераторы и делает порядок обработки зависимым от порядка вызова. Для проекта с требованием полного детерминизма это фатально.

Необходимо: `enqueue()` вместо `trigger()`, дренаж очереди в явной фазе кадра, лимит каскада. Ничего из этого в плане нет, хотя это и есть суть событийной архитектуры — всё остальное детали.

**5. «Сервисы — глобальные тяжеловесные системы, подписанные на события».**
Такое определение ведёт прямо к god-контейнеру: глобальный объект, подписанный на всё, мутирующий мир в произвольном порядке, нетестируемый в изоляции. Модуль должен быть **владельцем лайфцикла и точкой регистрации** (типы, команды, системы, подписки), а не «глобальным менеджером, который перемалывает данные».

**6. План не трогает корневые проблемы.**
Ни двойной источник правды, ни мёртвый `Application`, ни 44-килобайтный `EraApp`, ни три карты сущностей, ни отсутствие тестов. Он добавляет два новых модуля поверх существующей структуры и рефакторит одно действие. Через месяц проблемы останутся теми же, плюс два новых модуля, построенных на неверном фундаменте.

**7. Это промпт на генерацию кода, а не архитектурный план.**
«Выдавай код пошагово», «начни с интерфейсов», «не сломай рендер» — это инструкции исполнителю. В плане отсутствуют: граф слоёв, правила владения данными, контракт потока данных, порядок фаз кадра, критерии приёмки этапов, стратегия миграции без поломки существующих приложений. То есть именно то, что и требовалось.

### Вердикт

План не вредный, но преждевременный и построен на неверной модели (`entt::snapshot` с автообходом) и на стёртой границе Command/System. Выполнение в предложенном порядке приведёт к переписыванию Save/Load дважды.

## 4. Стратегия миграции

**Метод: strangler fig.** Новая архитектура строится рядом со старой, потребители переводятся по одному, старый код удаляется, когда перестал использоваться.

**Инвариант, действующий на каждом этапе:**

> После завершения любого этапа `sandbox.exe` и `era_sandbox.exe` собираются и работают. Все тесты зелёные. Этап, нарушивший это, не принят и откатывается целиком.

Порядок этапов продиктован зависимостями, а не удобством. Менять порядок нельзя.

## 5. Этапы

### Этап 0 — Подготовка. Без изменения поведения

- Создать `tests/`, включить `ENGINE_BUILD_TESTS` по умолчанию, подключить doctest или Catch2.
- Смок-тесты: оба приложения запускаются в headless-режиме, прогоняют 100 кадров, выходят с кодом 0.
- Зафиксировать `/fp:precise` в `cmake/CompilerOptions.cmake`, запретить fast-math.
- Завести `docs/adr/` для будущих решений.
- Создать пустые таргеты `engine_foundation`, `engine_world`, `engine_runtime` и прописать их в граф слоёв.

**Приёмка:** обе сборки зелёные; `ctest` проходит; новых зависимостей между слоями не появилось.

---

### Этап 1 — Фундамент. Новый код, старый не трогаем

Реализовать в `engine/foundation/`, ни с чем пока не интегрируя:

- `Handle<Tag>` + `HandlePool<T>` (слот 0 = заглушка, generation-счётчик)
- `TypeRegistry` + макросы `ENGINE_COMPONENT` / `ENGINE_FIELD` (поверх `entt::meta`)
- `EventBus` (только `enqueue`, `sink`, `drain(maxPasses)`)
- `Rng` (PCG, потоки по `RngStream`)
- `Result<T, E>` / `CmdResult`
- Стабильный строковый хеш (FNV-1a, `constexpr`)

**Приёмка:** юнит-тесты на каждый тип, включая:
- `Handle`: хендл на освобождённый слот невалиден;
- `TypeRegistry`: round-trip компонента через бинарный и JSON формат;
- `EventBus`: события из обработчика уходят в следующий проход; превышение `maxPasses` логируется и не вешает процесс;
- `Rng`: два генератора с одним сидом дают идентичные последовательности из 10 000 значений.

Приложения не тронуты. Это важно: этап полностью обратим.

---

### Этап 2 — Runtime и модули. `era_sandbox` переезжает на каркас

- `IModule`, `ModuleRegistry` (топологическая сортировка по `dependsOn`), `Engine`.
- `FixedTimestepLoop`: тик 30 Гц, `kMaxTicksPerFrame = 5`, интерполяция по alpha.
- Разобрать `EraApp::initEngine()` на модули: `PlatformModule`, `RenderModule`, `AudioModule`, `VfxModule`, `UiModule`.
- `EraApp` превращается в ~50 строк: список модулей + стартовая сцена.
- `SandboxApp` пока не трогаем.

**Приёмка:** `era_sandbox` визуально идентичен; `EraApp.cpp` < 5 КБ; ни одного `init`/`shutdown` вызова подсистем вручную; FPS не хуже прежнего; смок-тест зелёный.

---

### Этап 3 — Состояние города переезжает в ECS

Самый важный и самый рискованный этап. Делать одним куском нельзя — только по подсистемам, каждая с проверкой.

**3a. Здания.**
`BuildingInstance` → компоненты: `GridPos`, `BuildingRef`, `Production`, `Residence`, `LocalStorage`.
`m_buildingEntities` удаляется. Пространственный индекс «клетка → entity» становится ресурсом мира, перестраиваемым из registry.

**3b. Курьеры.**
`CarrierAgent` → компоненты: `Carrier`, `MovementPath`, `Cargo`, `TransformLocal`, `TransformPrev`.
`m_carrierEntities` удаляется.

**3c. Индикаторы алертов.**
`BuildingStatusEvent` + `m_alertEntities` → компонент `Alert` на самом здании + система, спавнящая визуальный индикатор.

**3d. Удаление `CitySimulation`.**
Класс перестаёт существовать. Его методы становятся системами: `tickProduction`, `tickConsumption`, `tickCarriers`, `updateAggregateStats`. Шесть `std::function`-колбэков заменяются событиями через `EventBus`.

**Приёмка после каждого подэтапа:** поведение идентично на глаз и по цифрам (население, ресурсы, счастье при одинаковом сценарии). После 3d: в проекте не остаётся ни одного `unordered_map<uint32_t, entt::entity>` и ни одного `std::function`-колбэка между подсистемами — проверяется грепом.

---

### Этап 4 — Команды и UI

- `CommandRegistry`. Команды: `PlaceBuildingCmd`, `DemolishBuildingCmd`, `EvolveEraCmd`, с парой `validate`/`apply`.
- Фаза `CommandDispatch` в тике.
- `renderUi()` разбирается на панели в `apps/era_sandbox/src/ui/`, каждая — `draw(const World&, CommandQueue&)`.
- Подсветка валидности места под курсором вызывает ту же `validate`, что и постановка. Дублирующая проверка удаляется.

**Приёмка:** UI-код не содержит ни одной мутации мира (грепом: `registry()` без `const` в `ui/` — запрещено); каждая команда покрыта тестом на успех и на каждый код отказа; ни одна панель не длиннее 150 строк.

---

### Этап 5 — Детерминизм

- Убрать `unordered_map`/`unordered_set` из игровой логики.
- `Rng` в стейт мира, все случайности через него.
- Системы принимают `Tick`, не `float dt`. `Time::delta()` недоступен из `world/` и `modules/` (проверяется на уровне включений).
- Запись лога команд + воспроизведение.
- Хеш мира: FNV-1a по всем зарегистрированным компонентам в порядке возрастания entity id.

**Приёмка:** `tests/determinism/` — реплей 10 000 тиков даёт эталонный хеш; два прогона подряд в одном процессе и два прогона в разных процессах дают одинаковый результат; тест включён в `ctest`.

---

### Этап 6 — Рефлексия и Save/Load

Только теперь, когда состояние унифицировано, типы зарегистрированы и детерминизм проверяется.

- Все компоненты регистрируются в `registerTypes()` своих модулей.
- `SaveModule`: бинарный формат (основной) + JSON (дебаг и git-diff сцен).
- Версия схемы на компонент + функции миграции.
- Поля `transient`: `TransformWorld`, `TransformPrev`, GPU-хендлы. Ресурсы сохраняются по пути/имени, хендл резолвится при загрузке.
- Старый `SceneSerializer` и `SceneResourceContext` **удаляются**.

**Приёмка:** round-trip save → load → хеш мира совпадает; сейв, сделанный со старой версией схемы компонента, корректно мигрируется (тест); незарегистрированный компонент даёт предупреждение при сейве; `SceneSerializer.cpp` отсутствует в репозитории.

---

### Этап 7 — Данные вместо хардкода

- `EraData.cpp` (10 КБ захардкоженных зданий, рецептов, эпох) → `assets/data/*.json`.
- `DataModule` + `DataRegistry`: загрузка, валидация схемы с внятными ошибками, горячая перезагрузка.
- Идентификаторы — строки в файлах, стабильные хеши в рантайме. `enum class BuildingType` удаляется.
- В сейвах — хеш строкового id, не порядковый номер.

**Приёмка:** новое здание добавляется правкой JSON без перекомпиляции; битый JSON даёт сообщение с именем файла, строкой и причиной; горячая перезагрузка по клавише работает в рантайме; старые сейвы читаются.

### Этап 8 — Универсальные модули

Каждый — **с реальным применением в `era_sandbox` в том же этапе**. Без применения модуль не пишется.

| Модуль | Обязательное применение |
|---|---|
| `EconomyModule` | заменяет `ResourceBundle`: склад, налоги, стоимость строительства; транзакции — команды |
| `TimerModule` | циклы производства и потребления жителей, по тикам |
| `SpatialModule` | индекс грида, поиск ближайшего свободного курьера |
| `StateMachineModule` | состояния курьера Idle / EnRoute / Returning |

**Приёмка:** для каждого модуля в тестах есть сценарий использования из `era_sandbox`; ни один модуль не содержит игровых терминов; `ResourceBundle` и `enum class ResourceType` удалены.

### Этап 9 — `sandbox` на новое ядро

Последним, потому что он сложнее (физика, персонаж, гизмо) и потому что к этому моменту каркас проверен на `era_sandbox`.

- `SandboxApp` → модули. `PhysicsModule`, мост физики переезжает в `world/bridges/`.
- `InputMap::Action` из ядра: остаётся обобщённый `ActionId` (хеш строки), конкретный список действий объявляет приложение.
- Мёртвый `engine::Application` удаляется.
- `engine/core` разделяется на `engine/platform` (L0) и `engine/foundation` (L1); `entt` уходит из платформенного слоя.

**Приёмка:** grep по `engine/` не находит игровых терминов (`Teapot`, `Shoot`, `Kick`, `Building`, `Woodcutter`); `Application.hpp` отсутствует; CI-проверка графа слоёв зелёная.

### Этап 10 — Редактор

- ImGui-инспектор поверх `TypeRegistry` — поля рисуются по описанию типа, без ручного кода на компонент.
- Undo/redo через diff состояния компонента.
- Сохранение/загрузка сцен через `SaveModule` (уже готов).

**Приёмка:** новый компонент появляется в инспекторе **без единой строки UI-кода**. Это главный тест всей архитектуры — если он не проходит, реализация рефлексии неверна.

## 7. Правила для агента-исполнителя

Эти правила обязательны. Нарушение — основание отклонить работу целиком.

**Процесс**
1. Один этап = одна порция работы. Не начинать следующий, пока предыдущий не принят человеком.
2. В конце каждого этапа: обе сборки зелёные + все тесты зелёные. Иначе этап не принят.
3. Если этап требует больше ~2000 строк изменений — разбить и согласовать разбивку до начала.
4. Перед началом этапа — перечитать `ARCHITECTURE.md`, раздел 16 (чек-лист запретов).

**Код**
5. Новый публичный тип — с юнит-тестом в той же порции работы. Без исключений.
6. Не добавлять универсальный модуль, у которого нет реальной точки применения в `era_sandbox` в этом же этапе.
7. Не «улучшать» Vulkan-рендер. `PbrRenderer`, `PostProcessPipeline`, `VulkanContext` вне зоны рефакторинга до этапа 10. Меняется только то, кто их вызывает.
8. Не удалять старый код, пока новый не доказал работоспособность. Сначала переключить потребителей, потом удалить.
9. Файл длиннее ~500 строк или функция длиннее ~80 — признак того, что декомпозиция не сделана.

**Запрещено безусловно**
10. Новые `std::function`-колбэки как связь между подсистемами.
11. `dispatcher.trigger()` в игровом коде — только `enqueue()`.
12. `std::unordered_map` / `unordered_set`, по которым итерируются в игровой логике.
13. Сырые `uint32_t` как хендлы ресурсов.
14. `#include` из вышестоящего слоя.
15. Игровая терминология в `engine/`.
16. Мутация мира из ImGui-кода.
17. Игровое состояние вне `entt::registry`.

**Коммуникация**
18. Если требование `ARCHITECTURE.md` мешает выполнить задачу — **остановиться и сказать об этом**, а не обходить молча. Обнаруженное противоречие фиксируется как ADR в `docs/adr/`, документ правится, и только потом пишется код.
19. Не заявлять о свойствах, которых нет в коде. Формулировка «полностью отвязано через события» допустима только если можно добавить второго слушателя, не трогая источник. Это проверяемый критерий — проверять до того, как писать в отчёте.
