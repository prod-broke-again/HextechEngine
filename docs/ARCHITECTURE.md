# Hextech Engine — Архитектура ядра

**Статус:** целевая архитектура. Действует с момента принятия.
**Версия:** 1.0
**Аудитория:** любой разработчик или AI-агент, который пишет код в этом репозитории.

Этот документ — **конституция**. Он описывает не «как сделать фичу X», а **правила, которые нельзя нарушать**, и **контракты, на которые опирается всё остальное**. Если код противоречит этому документу — неправ код.

Сопутствующий документ: `docs/REFACTORING_BRIEF.md` — диагноз текущего состояния и поэтапный план миграции.

## 0. Фундаментальные решения

Эти решения приняты и не пересматриваются без явного пересмотра всего документа.

| Решение | Значение | Последствия |
|---|---|---|
| **Детерминизм** | Полный. Одинаковый ввод → бит-в-бит одинаковый результат на одной платформе/сборке. | Фиксированный тик, RNG в стейте, запрет на `unordered_map` в игровой логике, запрет на wall-clock в симуляции. |
| **Редактор** | Планируется полноценный (инспектор, правка компонентов, сцены, undo/redo). | Нужен слой рефлексии типов. Он же обслуживает сейвы, JSON-данные и будущую сетевую репликацию. |
| **Скриптинг** | Нет. Логика на C++, данные в JSON с горячей перезагрузкой. | Нет FFI-границы, нет риска для детерминизма, нет цены на биндинги. Точка расширения под Lua заложена, но не реализуется. |
| **ECS** | EnTT. `entt::registry` — единственный владелец игрового состояния. | Никаких параллельных `std::vector<GameObject>` рядом с registry. |
| **Рендер** | Vulkan, существующий `PbrRenderer` / `PostProcessPipeline`. | Вне зоны рефакторинга. Ядро не переписывает рендер, а перестаёт лезть в него напрямую из приложения. |

## 1. Слои и направление зависимостей

Зависимости строго однонаправленные: слой **N** может зависеть только от **N−1** и ниже. Обратная или «боковая» зависимость — ошибка архитектуры, и она должна быть ошибкой сборки (CMake-таргет просто не линкует то, чего не должен видеть).

```
L7  app          apps/*                  Сборка конкретной игры: список модулей, стартовая сцена
                 ──────────────────────
L6  modules      engine/modules/*        Фичи: save, economy, timers, spatial, data, statemachine
                 ──────────────────────
L5  runtime      engine/runtime/*        IModule, ModuleRegistry, Engine, FixedTimestepLoop
                 ──────────────────────
L4  world        engine/world/*          World, компоненты, системы, планировщик, команды
                 ──────────────────────
L3  subsystems   engine/render/          Vulkan (без знания об ECS)
                 engine/physics/         Jolt (без знания об ECS)
                 engine/audio/
                 engine/vfx/
                 engine/ui/              ImGui-слой (без знания об игровой логике)
                 ──────────────────────
L2  resources    engine/resources/       AssetManager, загрузчики, GPU-кэши за хендлами
                 ──────────────────────
L1  foundation   engine/foundation/      Handle, TypeRegistry, EventBus, Rng, Result, ids, math
                 ──────────────────────
L0  platform     engine/platform/        Окно, ввод, файлы, время, лог, конфиг
```

**Почему `runtime` ниже `modules`.** `runtime` объявляет интерфейс `IModule` и владеет циклом; `modules` этот интерфейс реализуют. Значит зависимость идёт «модуль → runtime», и runtime не должен знать ни об одном конкретном модуле. Если в `engine/runtime/` появился `#include` конкретного модуля — архитектура сломана.

### 1.1. Правило моста

**L3 не знает про L4.** Рендерер не знает слова «entity». Физика не знает слова «компонент».

Связь между L3 и L4 — только через **bridge-системы**, которые живут в L4 и знают обе стороны:

```
world/bridges/RenderBridge.cpp    читает ECS → заполняет RenderQueue для PbrRenderer
world/bridges/PhysicsBridge.cpp   синхронизирует TransformLocal ↔ Jolt body
world/bridges/AudioBridge.cpp     AudioSourceComponent → AudioEngine
```

Это уже частично так (`engine/physics/PhysicsBridge.cpp`), но мост лежит не в том слое. Он переезжает в L4.

### 1.2. Правило чистоты ядра

**В `engine/` не должно встречаться ни одного игрового термина.** Ни `Teapot`, ни `ShootSphere`, ни `BuildingType`, ни `Woodcutter`.

Проверка — грепом. Если grep по `engine/` находит слово из домена конкретной игры, это баг архитектуры, а не косметика.

Текущее нарушение для примера: `engine/core/include/engine/core/InputMap.hpp` содержит `enum class Action { SpawnTeapot, ShootSphere, KickObject, ... }`. Ядро знает о чайниках. Так быть не должно — `Action` становится обобщённым идентификатором (`ActionId` = хешированная строка), а конкретный список действий объявляет приложение.

## 2. Правило единственного источника правды

> **Всё игровое состояние живёт в `entt::registry`. Точка.**

Запрещено держать игровые данные в:
- членах класса приложения,
- `std::vector<SomeGameThing>` внутри «симуляции»,
- параллельных `unordered_map<id, entt::entity>`,
- статиках и синглтонах.

**Индексы допустимы, но только как производные кэши.** Пространственный индекс «клетка грида → сущность» — это ресурс мира, который **можно полностью перестроить из registry** и который **не сохраняется в сейв**. Если индекс нельзя выбросить и восстановить — это не индекс, это второй источник правды.

Почему это правило №1 по важности: любая рассинхронизация двух источников — это баг, который воспроизводится раз в час и ловится днями. Все текущие «карты сущностей» в `EraApp` — именно такая мина.

## 3. YAGNI: что мы отменяем, а что нет

Постановка «мы отключаем YAGNI» неточная и опасная — при буквальном применении она даёт бесконечную обобщённую архитектуру, которой никто не пользуется. Правильная формулировка:

> **YAGNI применяется к игровым фичам. YAGNI НЕ применяется к швам.**

### Три категории кода

**1. Шов (seam)** — граница, контракт, точка расширения.
Признак: *если не сделать сейчас, потом придётся править 10+ файлов, чтобы вставить.*
→ **Пишем заранее, всегда.**
Примеры: шина событий, реестр типов, лайфцикл модулей, система хендлов, фазы кадра, фиксированный тик.

**2. Универсальная фича** — механика, которая есть в ≥3 разных играх и имеет стабильный, известный контракт.
→ **Пишем, но только под реальное применение.**
Примеры: сейв/лоад, кошелёк валют, таймеры, стейт-машина, пространственный индекс, загрузка дефиниций из данных.

**3. Спекулятивная фича** — «а вдруг понадобится».
→ **Не пишем. Закладываем только шов.**
Примеры сейчас: инвентарь, квесты, диалоги, локализация, behaviour tree, мультиплеер, звуковые шины.

### Железное правило против «архитектуры ради архитектуры»

> **Универсальный модуль обязан иметь хотя бы одну реальную точку применения в `era_sandbox` в том же этапе, в котором он написан.**

Нет применения — не пишем. Это прямой ответ на вопрос «как писать фичу, если нет примера применения»: **никак**. Нельзя обобщать вслепую — получится API, который не подойдёт первому же реальному случаю. Сначала одно реальное применение, потом обобщение по второму, и только по третьему — окончательный контракт («правило трёх»).

Швы — исключение из этого правила, потому что у них цена ретрофита несоизмеримо выше цены ошибки в дизайне.

## 4. Кадр и тик

### 4.1. Два разных ритма

```
ТИК СИМУЛЯЦИИ — фиксированный, 30 Гц (kTickRate), детерминированный
КАДР РЕНДЕРА  — переменный, сколько вытянет GPU, интерполирует между тиками
```

Игровые системы **никогда** не видят `deltaTime`. Они видят `Tick`:

```cpp
struct Tick {
    uint64_t index;                       // порядковый номер тика от старта мира
    static constexpr float dt = 1.f / 30.f;  // КОНСТАНТА времени компиляции
};
```

`Time::delta()` остаётся, но доступен только рендеру и UI. Использование `delta()` в системе симуляции — нарушение, ломающее детерминизм.

### 4.2. Фазы тика

Порядок жёсткий. Это контракт, на который опирается всё:

```
1. InputCollect      Сырой ввод → ActionState. Никаких мутаций мира.
2. CommandDispatch   Валидация и применение команд. ЕДИНСТВЕННОЕ место,
                     где рождаются новые сущности и происходят «решения».
3. SimulationTick    Системы в явно заданном порядке (см. 6.2).
4. EventDrain        Дренаж очереди событий. Обработчики могут только
                     enqueue новые события — они уйдут в СЛЕДУЮЩИЙ тик.
5. PostTick          Применение отложенных create/destroy. Перестройка индексов.
```

Кадр рендера:

```
A. PollEvents / ввод в буфер
B. N × Tick   (N = сколько накопилось; см. 4.3)
C. Interpolate (alpha = остаток аккумулятора / dt)
D. RenderBridge → PbrRenderer → PostProcess
E. UI (ImGui): читает мир const, шлёт команды в очередь следующего тика
```

### 4.3. Защита от спирали смерти

```cpp
constexpr int kMaxTicksPerFrame = 5;
```
Если накопилось больше — лишние тики **отбрасываются**, а не догоняются. Лучше замедлить игру, чем уйти в лавину. Факт отбрасывания логируется.

### 4.4. Интерполяция

Для всего, что двигается, компонент хранит два состояния:

```cpp
struct TransformLocal  { vec3 translation; quat rotation; vec3 scale; };  // текущий тик
struct TransformPrev   { vec3 translation; quat rotation; };              // предыдущий тик
```

`RenderBridge` строит матрицу из `lerp(prev, current, alpha)`. Это позволяет держать симуляцию на 30 Гц и рисовать на 200 FPS без рывков.

`TransformPrev` **не сохраняется** в сейв — восстанавливается копией из `TransformLocal`.

## 5. События

### 5.1. Только очередь, никогда не колбэк

Текущий код использует три разных механизма оповещения: `entt::dispatcher` (для одного события), шесть `std::function`-слотов в `CitySimulation` и прямые вызовы. Остаётся **один**.

```cpp
class EventBus {
public:
    template<class E> void enqueue(E&& e);           // РАЗРЕШЕНО везде
    template<class E> auto sink();                   // подписка при регистрации модуля
    void drain(int maxPasses = 8);                   // вызывает ТОЛЬКО движок, в фазе 4
private:
    entt::dispatcher m_dispatcher;
};
```

**`trigger()` (синхронная отправка) в игровом коде запрещён.** Причины:
- мутация registry посреди итерации `view` — невалидные итераторы, UB;
- порядок обработки становится зависимым от порядка вызова, а не от объявленного порядка → недетерминизм;
- каскад событий превращается в глубокий стек и неотлаживаемую цепочку.

Синхронный `trigger` допустим только в UI-слое и в редакторе, где кадр уже закончен.

### 5.2. Лимит каскада

`drain()` выполняет не более `maxPasses` проходов. События, порождённые обработчиками внутри дренажа, обрабатываются на следующем проходе. При исчерпании лимита — `LogLevel::Warn` со списком типов событий в очереди. Без этого лимита взаимно порождающие события вешают кадр насмерть.

### 5.3. Два вида событий

| | Сигнал (Notification) | Запрос (Command) |
|---|---|---|
| Направление | «случилось» | «сделай» |
| Кто шлёт | системы, команды | UI, ввод, ИИ |
| Обработчиков | 0..N | ровно 1 |
| Может отказать | нет | да, с кодом ошибки |
| Пример | `BuildingPlaced` | `PlaceBuildingCmd` |

Это разные механизмы. Не смешивать. Событие-сигнал никогда не отменяется и никогда не «выполняется».

### 5.4. Событие — это данные, а не указатель

```cpp
struct BuildingPlaced {
    entt::entity entity;
    GridPos      pos;
    BuildingId   type;
};
```

Событие обязано быть POD-подобной структурой без указателей на чужую память и без `std::function`. Оно должно быть сериализуемо: события — это то, что пишется в лог реплея.

## 6. Command, System, Module — три разные сущности

Это ключевое разделение. Аналогия с Laravel полезна, но её нельзя переносить буквально: в Laravel любое действие — это один HTTP-запрос, и цена объекта неважна. В игре есть горячий цикл, и «всё есть Action» даст катастрофу по производительности и по читаемости.

### 6.1. Command — дискретное намерение

**Когда:** 0–100 раз за тик. Приходит извне симуляции: UI, ввод, ИИ, будущая сеть.

```cpp
struct PlaceBuildingCmd {
    GridPos    pos;
    BuildingId type;
};

// Обязательная пара функций на каждую команду:
CmdResult validate(const World&, const PlaceBuildingCmd&);   // чистая, без мутаций
void      apply   (World&,       const PlaceBuildingCmd&);   // мутирует, шлёт события
```

Правила:
- `validate` — **чистая функция**. Не мутирует ничего. Может вызываться UI для подсветки «можно/нельзя» — ровно тот же код, что и при реальном применении. Никакого дублирования «проверки для UI» и «проверки при применении».
- `apply` вызывается **только** после успешной `validate`.
- Команда сериализуема → попадает в лог реплея → бесплатно даёт replay, undo и основу для сети.
- Команда не знает про рендер, ImGui, Vulkan.
- Команда — `struct` + две свободные функции, **не класс с виртуальными методами**. Виртуальность здесь не нужна, диспетчеризация — по типу через реестр.

**Почему не «класс с методом execute()»:** статeless-класс с одним методом — это функция с лишними церемониями. `struct данные + свободные функции` компилируется лучше, тестируется проще и естественно сериализуется.

### 6.2. System — обработка массивов

**Когда:** каждый тик, над тысячами сущностей.

```cpp
void tickProduction(World& world, Tick tick);
```

Правила:
- Свободная функция `(World&, Tick)`.
- **Не создаёт и не удаляет сущности напрямую.** Только через `world.deferred()` — применится в фазе 5.
- Объявляет, какие компоненты читает и какие пишет. Планировщик использует это для проверки конфликтов и (позже) для параллелизации.
- Порядок систем задан **явным списком**, а не порядком регистрации модулей. Список — часть конфигурации мира, он виден в одном месте и он же гарантирует детерминизм.

```cpp
scheduler.add({
    .name  = "production",
    .fn    = &tickProduction,
    .reads = {ct<BuildingType>()},
    .writes= {ct<Production>()},
    .after = {"consumption"},
});
```

### 6.3. Module — владелец лайфцикла

Вот это и есть «сервис» в смысле Laravel, но его работа — **не «перемалывать массивы»**, а владеть и регистрировать.

```cpp
class IModule {
public:
    virtual ~IModule() = default;
    virtual std::string_view name() const = 0;
    virtual std::span<const std::string_view> dependsOn() const { return {}; }

    virtual void registerTypes   (TypeRegistry&)    {}  // компоненты + их поля
    virtual void registerCommands(CommandRegistry&) {}
    virtual void registerSystems (SystemScheduler&) {}
    virtual void registerEvents  (EventBus&)        {}  // подписки

    virtual void onAttach(World&) {}   // создание ресурсов мира
    virtual void onDetach(World&) {}   // освобождение, в обратном порядке
};
```

Приложение становится списком модулей:

```cpp
int main() {
    Engine engine;
    engine.use<PlatformModule>();
    engine.use<RenderModule>();
    engine.use<PhysicsModule>();
    engine.use<AudioModule>();
    engine.use<VfxModule>();
    engine.use<SaveModule>();
    engine.use<EconomyModule>();
    engine.use<CityModule>();        // фича конкретной игры
    return engine.run();
}
```

Порядок `onAttach` выводится топологической сортировкой по `dependsOn()`. `onDetach` — в обратном порядке. **Ручной `initEngine()` на 70 строк и ручной `shutdownEngine()` перестают существовать.**

### 6.4. Сводная таблица

| | Command | System | Module |
|---|---|---|---|
| Частота | 0–100 / тик | каждый тик | 1 раз за запуск |
| Форма | struct + validate/apply | свободная функция | класс с виртуальными методами |
| Состояние | нет | нет | владеет ресурсами |
| Может отказать | да | нет | нет |
| Сериализуется | да | — | — |
| Создаёт сущности | да | только deferred | в onAttach |

## 7. World

```cpp
class World {
public:
    entt::registry&       registry();
    const entt::registry&  registry() const;

    EventBus&    events();
    DeferredOps& deferred();     // отложенные create/destroy
    Rng&         rng(RngStream); // детерминированный, в стейте мира
    Tick         tick() const;

    template<class T> T&       resource();       // singleton-данные мира
    template<class T> const T& resource() const;
};
```

**Ресурс мира** — то, что существует в единственном экземпляре и не привязано к сущности: пространственный индекс, кошелёк, текущая эпоха, настройки симуляции. Живёт в `entt::registry` через `registry.ctx()` — это по-прежнему один источник правды.

**DeferredOps** — буфер, чтобы системы не ломали итерацию:

```cpp
world.deferred().destroy(e);
auto e = world.deferred().create();   // «обещанная» сущность, реальная в фазе 5
```

## 8. Рефлексия типов — фундамент, а не фича

### 8.1. Развенчание мифа

> «EnTT snapshot автоматически соберёт все компоненты сущностей и сдампит их»

**Это неверно.** `entt::snapshot` требует явно перечислить каждый тип компонента в точке вызова:

```cpp
snapshot.get<TransformLocal>(out).get<MeshComponent>(out).get<...>(out);
```

В C++ нет рефлексии. «Автоматически» не бывает — бывает «один раз объявили, дальше везде бесплатно». Любой план, обещающий автоматический обход компонентов без слоя регистрации, построен на несуществующей возможности.

### 8.2. Одна регистрация — пять применений

```cpp
ENGINE_COMPONENT(TransformLocal)
    ENGINE_FIELD(translation)
    ENGINE_FIELD(rotation)
    ENGINE_FIELD(scale)
ENGINE_COMPONENT_END()
```

Из одной этой записи получаем:

1. **Бинарная сериализация** — сейв/лоад.
2. **JSON-сериализация** — сцены, дебаг, диффы в git.
3. **ImGui-инспектор** — редактор рисует поля сам, по типу.
4. **Diff двух состояний** — undo/redo в редакторе.
5. **Сетевая репликация** — потом, если понадобится.

Пять систем, которые иначе пришлось бы писать и синхронизировать вручную. Это самый дорогой для ретрофита шов в проекте — поэтому он делается **первым**, а не последним.

### 8.3. Реализация

Тонкий `TypeRegistry` поверх `entt::meta`. Своя обёртка нужна, чтобы:
- держать версию схемы на компонент (`version: 3`) и функции миграции между версиями;
- помечать поля как `transient` (не сохранять: `TransformWorld`, `TransformPrev`, GPU-хендлы);
- держать человекочитаемое имя и подсказку для редактора;
- не тащить `entt::meta` в каждый файл.

```cpp
struct FieldDesc {
    std::string_view name;
    TypeId           type;
    size_t           offset;
    bool             transient = false;
};

struct ComponentDesc {
    std::string_view          name;
    uint32_t                  version;
    std::vector<FieldDesc>    fields;
    void (*migrate)(void* data, uint32_t fromVersion);
};
```

### 8.4. Правило регистрации

**Каждый компонент регистрируется в `registerTypes()` своего модуля.** Незарегистрированный компонент не сохраняется, не виден в редакторе и вызывает предупреждение при первом сейве. Регистрация — часть определения компонента, а не отдельная задача «потом».

## 9. Хендлы вместо сырых индексов

Текущий код: `uint32_t mesh = UINT32_MAX` как «невалидный», плюс отдельная константа `kInvalidGpuMesh`. Это уже дало реальный баг: проверка `if (meshId == 0) return;` заблокировала валидный меш с индексом 0.

```cpp
template<class Tag>
struct Handle {
    uint32_t index      = 0;   // 0 — ВСЕГДА невалиден
    uint32_t generation = 0;   // защита от use-after-free слота

    explicit operator bool() const { return index != 0; }
    bool operator==(const Handle&) const = default;
};

using MeshHandle     = Handle<struct MeshTag>;
using TextureHandle  = Handle<struct TextureTag>;
using MaterialHandle = Handle<struct MaterialTag>;
```

Правила:
- **Слот 0 всегда занят** заглушкой: розовый «missing» меш, пурпурная шахматка вместо текстуры. Промах ресурса виден глазами, а не падает.
- `generation` инкрементируется при освобождении слота → старый хендл становится невалидным детерминированно, а не молча указывает на чужой ресурс.
- Типизация не даёт передать `TextureHandle` туда, где ждут `MeshHandle`. Сейчас оба — `uint32_t`, и компилятор молчит.
- Хендлы **не сохраняются в сейв напрямую** — сохраняется путь/имя ресурса, хендл резолвится при загрузке (поле помечается `transient`, рядом лежит `assetPath`).

## 10. Детерминизм: правила

Раз выбран полный детерминизм, он превращается в набор запретов. Нарушение любого — молчаливый баг, который проявится через месяц на чужой машине.

### 10.1. Запрещено в игровой логике

| Запрещено | Почему | Чем заменить |
|---|---|---|
| `Time::delta()` | плавающий шаг | `Tick::dt` (константа) |
| `std::unordered_map/set` **для итерации** | порядок не гарантирован между запусками, компиляторами, вставками | `std::map`, отсортированный `std::vector`, `entt::dense_map` с явной сортировкой |
| `rand()`, `std::random_device`, глобальный `mt19937` | глобальный или недетерминированный стейт | `world.rng(stream)` |
| `std::chrono::now()` в симуляции | wall-clock | `tick.index` |
| Порядок `registry.view()` как значимый | зависит от истории вставок/удалений | явная сортировка по `entity` или `registry.sort<T>()` |
| Многопоточная запись без детерминированного слияния | гонка порядка | одна нить, либо детерминированный reduce |
| `-ffast-math` / `/fp:fast` | компилятор переставляет операции | `/fp:precise` (MSVC), зафиксировать в `cmake/CompilerOptions.cmake` |

### 10.2. RNG

```cpp
enum class RngStream : uint8_t { Simulation, Ai, Loot, Vfx, _Count };
```

Отдельный поток на подсистему, чтобы косметика (VFX) не сдвигала игровую последовательность. PCG или xoshiro — простые, быстрые, с явным стейтом. Стейт всех потоков **сохраняется в сейв**.

### 10.3. Физика

Jolt детерминирован при фиксированном шаге **на одной платформе и одной сборке**. Кросс-платформенный детерминизм не гарантируется и **не заявляется**. Если позже понадобится лок-степ мультиплеер между разными ОС — физика выносится из детерминированного контура (становится косметикой), а игровая логика работает на собственной упрощённой модели.

Записано здесь явно, чтобы это не вскрылось сюрпризом.

### 10.4. Тест детерминизма

Не «мы старались», а автоматическая проверка:

```
tests/determinism_test.cpp
  1. Загрузить фиксированный стартовый мир (seed + сцена).
  2. Проиграть записанный лог команд на 10 000 тиков.
  3. Посчитать хеш мира (FNV-1a по всем зарегистрированным компонентам
     в детерминированном порядке сущностей).
  4. Сравнить с эталонным хешем в репозитории.
```

Тест падает → детерминизм сломан → PR не принимается. Без этого теста правила из 10.1 разъедутся за две недели.

## 11. UI

### 11.1. UI не принимает решений

Панель имеет ровно два права:
1. читать мир **через `const World&`**;
2. класть команды в очередь.

Панель **не может**: мутировать компоненты, вызывать системы, знать про `PbrRenderer`, хранить игровое состояние в своих полях.

Подсветка «можно/нельзя поставить здание» вызывает **ту же самую** `validate(world, cmd)`, что и реальная постановка. Дублирование правил валидации между UI и логикой запрещено.

Приятное следствие: UI находится вне детерминированного контура (раздел 10). Смена UI-библиотеки не может сломать симуляцию — по построению.

### 11.2. Два разных UI, которые нельзя смешивать

| | Инструментальный UI | Игровой UI |
|---|---|---|
| Что это | редактор, инспектор, дебаг-панели, профайлер | HUD, меню, док строительства, тултипы |
| Кто видит | разработчик | игрок |
| Идёт в релиз | нет | да |
| Требования | скорость написания, полнота | внешний вид, анимации, локализация, геймпад |
| Технология | **ImGui, навсегда** | заменяемый бэкенд |
| Абстрагируется | **нет** | да |

Это разделение есть во всех зрелых движках (Unity: IMGUI в редакторе, UI Toolkit в игре; Unreal: Slate в редакторе, UMG в игре). Попытка обслужить оба одной системой даёт либо уродливый игровой UI, либо мучительный редактор.

**Инструментальный UI абстрагировать запрещено.** Инспектор компонентов по `TypeRegistry` — это ровно та задача, ради которой существует immediate mode. Любая прослойка здесь только мешает.

### 11.3. Граница проходит по данным, а не по виджетам

Типичная ошибка — написать собственные `IButton` / `ILabel` / `IPanel` и подложить под них ImGui. Такая абстракция всегда получается по нижней границе возможностей: она не умеет ни того, что умеет ImGui, ни того, что умеет retained-библиотека, и протекает при первой же нетривиальной задаче.

Правильная граница — **доменная модель панели**:

```
const World  →  build<Model>(world)  →  IUiBackend::draw(model, cmdQueue)  →  Command
                 чистая функция           заменяемая реализация
```

Модель — это **конкретные данные конкретного экрана**, не обобщённое дерево виджетов:

```cpp
struct BuildOption {
    BuildingId   id;
    IconHandle   icon;
    CostList     cost;
    bool         affordable;
    bool         unlocked;
    std::string_view lockReason;   // пусто, если разблокировано
};

struct BuildDockModel {
    std::vector<BuildOption> options;
    BuildingId               selected;
    bool                     demolishMode;
};

// Чистая функция. Не знает ни про ImGui, ни про рендер. Тестируется юнит-тестом.
BuildDockModel buildDockModel(const World& world);
```

Что это даёт:
- **Модель тестируется** без графики: «при нехватке дерева опция лесопилки имеет `affordable == false`».
- **Смена бэкенда не трогает логику.** ImGui-бэкенд рисует список кнопок; будущий кастомный — спрайты с анимацией. Модель одна и та же.
- **Нет обобщения вслепую.** Мы не изобретаем универсальную систему виджетов под несуществующие требования.

```cpp
class IUiBackend {
public:
    virtual ~IUiBackend() = default;
    virtual void draw(const BuildDockModel&,  CommandQueue&) = 0;
    virtual void draw(const ResourceModel&,   CommandQueue&) = 0;
    virtual void draw(const InspectorModel&,  CommandQueue&) = 0;
};
```

Интерфейс растёт по одному методу на экран. Это намеренно: экранов в игре десятки, а не тысячи, и явный список честнее обобщённого дерева.

### 11.4. `UiDrawList` — шов в рендерере

Любая UI-библиотека в конечном счёте выдаёт одно и то же: **список вершин, индексы, текстура, scissor-прямоугольник**. Это общий знаменатель ImGui, RmlUi, Clay и любого собственного UI.

Рендерер принимает `UiDrawList`, а не `ImDrawData`:

```cpp
struct UiDrawCmd { uint32_t indexOffset, indexCount; TextureHandle texture; Rect scissor; };
struct UiDrawList { std::vector<UiVertex> vertices; std::vector<uint16_t> indices; std::vector<UiDrawCmd> cmds; };
```

`ImGuiLayer` превращается в один из поставщиков `UiDrawList`. Смена UI-библиотеки после этого не трогает ни строчки Vulkan-кода. Шов дешёвый (тонкий адаптер), ретрофит дорогой — поэтому закладывается сразу.

### 11.5. Структура

```
engine/ui/                        L3   UiDrawList, IUiBackend, ImGuiBackend
apps/era_sandbox/src/ui/
    models/BuildDockModel.cpp          чистые функции World → Model
    models/ResourceModel.cpp
    models/InspectorModel.cpp
    backend_imgui/BuildDockView.cpp    отрисовка модели, единственное место с ImGui::
```

Одна модель — один файл, одна функция. Одна view — один файл, ≤150 строк. Текущий монолитный `renderUi()` на 335 строк внутри класса приложения — ровно то, что этим устраняется.

### 11.6. Чего сейчас не делаем

Второй UI-бэкенд **не пишется**, пока нет реального игрового UI (раздел 3: это спекулятивная фича). В песочнице весь текущий «UI» — инструментальный, и ему ImGui подходит идеально.

Закладываются только три шва: `UiDrawList`, доменные модели, `IUiBackend`. Суммарно это тонкий адаптер и разделение уже существующего кода на «вычислить» и «нарисовать» — почти нулевая дополнительная работа сегодня и открытая дверь завтра.

## 12. Данные вместо хардкода

Логика на C++, **данные в JSON**. Всё, что является балансом или контентом, уезжает из кода:

```
assets/data/
    buildings.json     типы зданий, стоимость, размер, требования эпохи
    recipes.json       производственные цепочки
    resources.json     ресурсы и валюты
    eras.json          эпохи и условия перехода
```

```cpp
class DataRegistry {
public:
    void load(const std::filesystem::path& dir);
    void reload();                       // горячая перезагрузка по F5
    const BuildingDef& building(BuildingId) const;
};
```

Правила:
- Идентификатор — **строка в файле**, `uint32_t` хеш в рантайме. Не `enum`. Enum требует перекомпиляции и ломает сейвы при перестановке значений.
- В сейв пишется **строковый id или его стабильный хеш**, никогда не порядковый номер enum.
- Горячая перезагрузка обязана быть с первого дня — иначе балансировка превращается в цикл «правка → 3 минуты сборки».
- Валидация схемы при загрузке с внятной ошибкой («recipes.json:42: unknown resource 'bronzee'»), а не падение в рантайме через 10 минут игры.

Текущий `apps/era_sandbox/src/Simulation/EraData.cpp` — 10 КБ захардкоженных зданий и рецептов. Он целиком переезжает в JSON.

## 14. Тестирование

Минимум, ниже которого не опускаемся:

| Что | Как |
|---|---|
| foundation (Handle, TypeRegistry, EventBus, Rng) | юнит-тесты, 100% публичного API |
| Каждая команда | тест на `validate`: успех + каждый код отказа |
| Сериализация | round-trip: save → load → хеш мира совпадает |
| Детерминизм | реплей 10 000 тиков → эталонный хеш |
| Загрузка данных | битый JSON → внятная ошибка, не падение |
| Сборка приложений | смок-тест: запуск, 100 тиков, выход с кодом 0 |

Правило: **новый публичный тип — с тестом в том же PR.** Не «потом напишем тесты».

## 16. Запрещённые практики (чек-лист ревью)

Любой PR, содержащий что-либо из списка, отклоняется:

- [ ] Игровое состояние вне `entt::registry`
- [ ] Параллельный контейнер «id → entity», который нельзя перестроить из registry
- [ ] `std::function`-колбэк как связь между подсистемами
- [ ] `dispatcher.trigger()` в игровом коде (вместо `enqueue`)
- [ ] `Time::delta()` в системе симуляции
- [ ] `std::unordered_map`, по которому итерируются в игровой логике
- [ ] `rand()`, `std::random_device`, глобальный генератор
- [ ] Сырой `uint32_t` как хендл ресурса
- [ ] `#include` из вышестоящего слоя
- [ ] Игровой термин в `engine/`
- [ ] Мутация мира из ImGui-кода
- [ ] Дублирование правил валидации между UI и командой
- [ ] Файл длиннее ~500 строк
- [ ] Функция длиннее ~80 строк
- [ ] Новый публичный тип без теста
- [ ] Новый универсальный модуль без реального применения в приложении
- [ ] Компонент без регистрации в `TypeRegistry`
- [ ] Захардкоженный баланс/контент вместо JSON

## 17. Что этот документ сознательно НЕ предписывает

Чтобы не путать швы со спекуляцией:

- **Мультиплеер.** Команды сериализуемы и симуляция детерминирована — этого достаточно как задела. Сетевой код не пишем и его абстракции не закладываем.
- **Многопоточность систем.** `SystemScheduler` объявляет read/write множества, что позволит распараллелить позже. Сейчас исполнение однопоточное. Параллелизм без профилирования — преждевременная оптимизация.
- **Скриптинг.** Данные в JSON закрывают ~80% нужд. Точка расширения — `CommandRegistry`: скрипт, если появится, будет просто ещё одним источником команд. Специально ничего под него не строим.
- **Переписывание рендера.** `PbrRenderer` и `PostProcessPipeline` работают. Их внутренности вне зоны рефакторинга. Меняется только то, кто и как их вызывает.
- **Кастомные аллокаторы, job system, ECS «побыстрее».** Пока нет измеренной проблемы производительности — нет и задачи.

## 18. Как этим пользоваться

1. Пишешь новый код — сначала определи слой. Затем проверь по разделу 16.
2. Появилась новая механика — она Command, System или Module? Раздел 6.
3. Появился новый компонент — зарегистрируй его в `registerTypes()` модуля. Раздел 8.4.
4. Хочешь добавить универсальный модуль — найди реальное применение в `era_sandbox`. Нет применения — не добавляй. Раздел 3.
5. Хочешь нарушить правило — напиши ADR в `docs/adr/` с обоснованием и правь этот документ. Молча нарушать нельзя.
